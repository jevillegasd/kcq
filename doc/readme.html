kcq User Manual

A layout-driven KLayout Salt package for circuit quantum electrodynamics (cQED) design.

This manual is for people using kcq to design cQED chips: installing the package, placing components, routing, and (as later phases land) extracting netlists and piping layouts to simulation. If you're looking to work on kcq's own source instead — architecture, coding standards, running the test suite — see README.md at the repository root.

1. Introduction

kcq replaces hardcoded, legacy layout approaches to circuit QED chip design with a layout-driven philosophy, in the spirit of SiEPIC-Tools: routing, component geometry, and (eventually) verification and simulation logic all live in a Python package, while every trace width, gap width, clearance, and bend radius is pulled from the active technology's XML files at runtime — never hardcoded in Python. Swapping technologies (a different fab process, different CPW dimensions) never requires touching kcq's own code.

Concretely, kcq gives you:

  • An octilinear (Manhattan + 45°) waypoint router with Euler-spiral and circular-arc bends, and adiabatic sine S-bends, so routed CPWs minimize radiation loss.
  • Technology-driven CPW synthesis and boolean ground-plane generation.
  • A default PDK (kcq) with a two-island "DiCarlo-style" transmon, a star-coupler transmon variant, Manhattan-style Josephson junctions and SQUIDs, and importable fixed cells (e.g. RF launchers).
  • A shared pin/port convention that lets the router, components, and (in later phases) LVS all agree on where things connect.
  • A metadata-pointer mechanism so simulation and experimental results can be attached to a design and recovered later — even after a round trip through GDS.

kcq is under active development. Sections below are marked available for what works today, or planned for designed-but-not-yet-built functionality — described so this manual stays a complete reference, not just a changelog.

2. Installation

Prerequisites

  • KLayout, matching or newer than the api-version declared in grain.xml (currently 0.28).
  • Nothing else, to just use the package. (Contributing to kcq itself needs a Python/uv setup — see the developer README.)

Installing the Salt package

The recommended path is KLayout's own Package Manager:

  1. In KLayout, open Tools → Manage Packages.
  2. Choose Install New Package → Install from File.
  3. Point it at the root of this repository (the folder containing grain.xml).
  4. Restart KLayout so it picks up the new technology and macros.

If you'd rather manage it manually, copy (or symlink) the repository into your KLayout installation's salt folder — consult KLayout's own documentation for the exact path on your OS, since it varies (typically somewhere under your home directory or %APPDATA% on Windows).

Current limitation. kcq's PCells and fixed cells aren't auto-registered on KLayout startup yet — that's a Phase 7 item (a $autorun macro calling kcq.utils.pcell_loader.register_library). Until then, run that call yourself once per session, from KLayout's macro editor/console or a script (shown next).

3. Getting started: your first design

This walks through placing a qubit, placing an edge launcher, and routing a feedline between them — entirely in Python, since that's what works reliably both inside KLayout's macro console and headlessly. (A GUI-driven workflow, with toolbar buttons and dialogs for this, is planned for Phase 7.) 

import pya
from kcq.utils import pcell_loader
from kcq.geometry import pins, router, cpw

# Registers every PCell and fixed cell from tech/kcq/ into a pya.Library
# named "kcq". Call this once per session.
pcell_loader.register_library("kcq")

layout = pya.Layout()
layout.dbu = 0.001
top = layout.create_cell("TOP")

# Place a qubit. Parameters left out use their documented defaults.
qubit = layout.create_cell("Transmon", "kcq", {
    "coupler_island": ["top"],
    "coupler_side": ["right"],
})
qubit_inst = top.insert(pya.CellInstArray(qubit.cell_index(), pya.Trans(0, 0)))

# Place an edge launcher a few hundred microns away. Fixed (static) cells
# use the two-argument create_cell -- no params dict, unlike a PCell.
launcher = layout.create_cell("launcher_15p5_7", "kcq")
launcher_inst = top.insert(pya.CellInstArray(
    launcher.cell_index(),
    pya.Trans(pya.Trans.R180, int(3000.0 / layout.dbu), int(120.0 / layout.dbu))))

# Read each instance's port back out, in TOP's coordinate system.
qubit_pin = pins.get_pins(qubit_inst.cell, layout)[0]
launcher_pin_local = pins.get_pins(launcher_inst.cell, layout)[0]
launcher_pin = pins.PinInfo(
    name=launcher_pin_local.name,
    position=launcher_inst.dcplx_trans * launcher_pin_local.position,
    angle_deg=(launcher_pin_local.angle_deg + launcher_inst.dcplx_trans.angle) % 360.0,
    width=launcher_pin_local.width,
)

assert pins.check_alignment(qubit_pin, launcher_pin), "ports don't face each other"

# Route between them and synthesize the CPW.
waypoints = router.route_octilinear(qubit_pin.position, qubit_pin.angle_deg,
                                     launcher_pin.position, launcher_pin.angle_deg,
                                     bend_radius=100.0)
feedline = cpw.CPW("kcq", "resonator", waypoints)
feedline.build(top, layout)

layout.write("my_first_chip.gds")

This script is verified against the actual API as part of kcq's own test suite (see tests/test_pdk_integration.py and tests/test_fixed_cells.py), so it's a safe starting point to copy and modify.

4. Layers and the default technology

kcq's default technology (kcq, at tech/kcq/) uses a negative-lithography convention for its shared base metal: what you (or kcq's own code) draws on the primary layer is the gap — the region etched away — not the metal itself. A separate, paired layer carries an explicit positive trace/island core for visualization and direct metal placement.

Every layer number in kcq means something structurally, not just by convention within one technology file:

  • Physical metal levels get a contiguous block of ten each. Level 1 (L1) is layers 0-9, level 2 (L2) is 10-19, level 3 would be 20-29, and so on — a layer's number tells you which physical level it fabricates onto before you've even looked up its name.
  • Everything else — every non-physical "metalayer" (pins, text, device recognition, ground exclusion, ...) — uses a layer number above 100, so a quick glance at the layer number alone tells you "fabricated metal" from "bookkeeping/annotation" with no lookup needed.
  • Layer 100 itself (multiple datatypes) is further reserved specifically for cell/chip/wafer-scale boundary definitions — things that describe the extent of something, not a signal path: device-recognition boxes, die/chip/wafer outlines, the usable design area, alignment marks, and e-beam writefield boundaries all live here, distinct from the routing/annotation metalayers above 100.

A second, independent axis applies within a given layer: the datatype has a fixed meaning of its own, the same way across every physical layer, so you don't have to memorize what a given layer's non-zero datatypes mean case by case.

DatatypeSuffixMeaning
0.drawingThe default, intended physical mask geometry — actual metal (positive or negative), actual implants, etc.
4.pin / .labelZero-width paths or small text boxes marking terminal connectivity — the basis for LVS/netlist extraction
5.blockage / .slotRegions where automated routers or slotting tools are prohibited from placing features
10 / 20.fill / .dummyDensity-fill or dummy patterning added late in the pipeline, for density-verification rules and/or flux traps before tape-out

This is why e-beam dose compensation has its own dedicated layer number (5, in the boundary-free part of L1's block) rather than living as an arbitrary non-zero datatype on the junction layer (2) as an earlier draft of this table had it: a non-zero datatype on any layer is meaningful under this convention, so anything that isn't a pin, blockage, or fill needs a layer of its own instead of overloading a datatype number that already means something else. kcq's own negative-lithography split (1/0=gap, 1/1=positive core) predates and is an explicit exception to this convention — datatype 1 there means "secondary drawing representation," not anything from the table above.

Physical metal — L1 (layers 0–9)

The only level with real, fabricated geometry today. Every row below is a real layer, not a reserved placeholder — though several (marked below) aren't emitted by any PCell yet even though the .lyp already defines them, ready for when a PCell needs them.

L2 (layers 10-19) is a flip-chip/multi-level routing placeholder: 10/0 is registered today in kcq.lyt's native KLayout connectivity stack (so KLayout's own Trace Net tool already understands it, with zero kcq code involved), but no PCell emits anything on it yet, and the via connecting it back to L1 has no real layer number assigned. L3 and beyond (20-29, 30-39, ...) are fully reserved, with nothing defined at all.

The rest of layer 100's cell/chip/wafer boundary datatypes (chip handling size, single-die outline, wafer outline, design area, die-level alignment marks, e-beam writefield boundary, ...), plus a couple of KLayout-GUI-only bookkeeping layers (black-box PCell size/name annotations), are .lyp-only conventions with nothing wired into any PCell yet — documented in tech/kcq/lyp/kcq.lyp directly; open it in KLayout's Layers panel for the full, colored list.

Trace widths, gap widths, ground clearances, bend radii, and routing style all live in tech/kcq/waveguides.xml, organized per named CPW "flavor" (feedline, resonator, flux_line in the default technology) — see Customizing the technology to add your own or adjust these.

5. Routing and waveguides

Pins and ports

Every connectable point in kcq — a PCell's coupler, a fixed cell's launch point — is marked with a pin: a short marker path on the PinRec layer (110/1) whose midpoint is the connection point and whose direction is the port's outward-facing orientation angle, plus a co-located name label on PinRecText (110/2). Read pins back out of any cell with kcq.geometry.pins.get_pins(cell, layout), which returns a list of PinInfo(name, position, angle_deg, width).

Two ports are correctly aligned for a direct connection when the second one's angle is the first's + 180° (within tolerance) — check this with kcq.geometry.pins.check_alignment(pin_a, pin_b) before routing, especially for fixed cells you've imported yourself.

The router

kcq.geometry.router.route_octilinear(p1, angle1, p2, angle2, bend_radius=...) returns a waypoint list connecting two ports, solved purely from their positions and outward angles — it picks the shortest of an L-shape (one corner), Z-shape (two corners), or U-shape (three corners, for ports that need a backtrack) route, using headings in 45° increments. route_manhattan(...) is the same solver restricted to axis-aligned (0/90/180/270°) headings, for technologies or components that need strict Manhattan routing.

There's no obstacle avoidance yet — the router solves purely from the two ports' own geometry. Keep this in mind on denser layouts.

kcq.geometry.curves.round_polyline(waypoints, radius, style="euler"|"arc") turns those sharp-cornered waypoints into a smoothed centerline, inscribing an Euler-spiral (minimizes radiation loss) or circular-arc bend at each corner — CPW.build (below) calls this for you, so you rarely need it directly. It raises a clear error if a bend doesn't fit in the space available, or if a corner would need an unsupported 180° hairpin turn.

CPW synthesis

kcq.geometry.cpw.CPW(tech_name, cpw_name, waypoints) builds the actual trace and gap-envelope Regions for a named CPW "flavor" from waveguides.xml, and .build(cell, layout) inserts them. Trace dimensions are never passed in directly: they always come from the technology, which is the whole point of "layout-driven" — the same script produces correctly-scaled output against any technology that defines a matching cpw_name.

6. The component library

All PCells below live in tech/kcq/pcells/ and are registered into the "kcq" library by pcell_loader.register_library. Place one with layout.create_cell(name, "kcq", params); any parameter you omit uses its default.

Transmon available

A DiCarlo-style two-island transmon: two rectangular islands stacked vertically (the junction/SQUID sits in the gap between them), with couplers as horizontal CPWs whose center conductor extends into a notch cut in an island's side edge, capacitively gapped from the remaining island metal at the notch's back wall.

Parameter groupKey parameters
Islandsisland_width, island_height, island_gap, corner_radius
Junction leadsadd_junction_leads, junction_pos_x, junction_y_offset, arm_width, arm_gap, arm_radius, lead_angled, junction_angle, squid_spacing
Couplers (parallel lists, one entry per coupler)coupler_island ("top"/"bottom"), coupler_side ("left"/"right"), coupler_y_offset, coupler_wg_width, coupler_wg_gap (default to the technology's resonator CPW dimensions if left empty), coupler_notch_depth, coupler_notch_gap, coupler_extension
Keepoutground_clearance, keepout_corner_radius, margin

Each coupler gets a pin named C0, C1, ... at its outer end. A metadata pointer (see Metadata) is attached automatically.

TransmonStar available

A concentric transmon with a circular island and N configurable radial couplers (star pattern), each independently controllable for angle, depth, gap, and angular width via parallel-list parameters (coupler_angles, coupler_depths, coupler_gaps, coupler_widths, ...). Useful where you want more couplers than the two-island Transmon's four sides comfortably support. Pins are named C0, C1, ... in coupler_angles order.

Manhattan available

A parametric Manhattan-style (double-angle-evaporation) Josephson junction: two fingers meeting at angle/inner_angle, with configurable widths (junction_width_t/junction_width_b), connector pads, and optional patch/bandage clearance cuts. Set negative_resist to match your lithography polarity; set draw_cap to also draw a standalone test capacitor pad.

ManhattanSQUID available

A SQUID loop built from two Manhattan sub-instances spaced by squid_spacing, with independent squid_asymmetry scaling the second junction's width, and a single shared test pad spanning both (rather than two overlapping ones).

7. Fixed cells (launchers and other static parts)

Static, pre-drawn geometry (RF wirebond launchers, alignment structures, ...) lives in tech/kcq/fixed_cells/ as GDS/GDS2/OASIS files, and is imported into the same "kcq" library alongside the PCells. Unlike a PCell, a fixed cell takes no parameters — create it with the two-argument form: 

launcher = layout.create_cell("launcher_15p5_7", "kcq")

Ports on an imported file have no PinRec markers by convention (they weren't drawn by kcq), so each fixed cell needs a same-named .json sidecar documenting its pins, applied automatically on import. For example, tech/kcq/fixed_cells/launcher_15p5_7.json, next to launcher_15p5_7.oas (an RF launcher tapering to a 15.5µm core / 7µm gap CPW): 

{
  "description": "RF wirebond launcher, tapering to a 15.5um core / 7um gap CPW at the connection port.",
  "pins": [
    {"name": "P1", "x": 0.0, "y": 0.0, "angle_deg": 0.0, "width": 29.5}
  ]
}

To add your own fixed cell: drop the GDS/GDS2/OASIS file and a matching .json sidecar (same file stem) into fixed_cells/, then call pcell_loader.register_library("kcq") again — it's idempotent, so this is safe to call repeatedly. width in the sidecar follows the same convention as everywhere else in kcq: the full envelope width (core + 2×gap), not just the trace core.

8. Customizing the technology

Everything dimensional — trace widths, gaps, ground clearances, bend radii, routing style — comes from waveguides.xml, not from Python. To add a new CPW "flavor" or change the defaults, edit tech/kcq/waveguides.xml: 

<cpw name="feedline" layer="1/1" gap_layer="1/0">
  <trace_width value="10.0"/>
  <gap_width value="6.0"/>
  <ground_clearance value="20.0"/>
  <bend_radius min="50.0" default="100.0" style="euler"/>
  <taper length="150.0"/>
  <routing style="octilinear"/>
</cpw>
XML comments in this file (and any kcq XML file) can't contain a literal -- — that's illegal per the XML spec, not a kcq restriction, but it's easy to trip over when hand-editing notes. Use a single dash or reword instead.

To develop against a different technology entirely (a second PDK, or a private fork of kcq), point the KCQ_TECH_PATH environment variable at a directory containing your own <name>/waveguides.xml and <name>/pcells/ — kcq's Python code resolves a technology by name in this order: a KLayout-registered technology, then KCQ_TECH_PATH, then the repository's own tech/ folder. This is also how kcq's own headless test suite runs without a full KLayout install.

9. Simulation & experimental metadata pointers available

Later phases will extract Energy Participation Ratios (EPR) and S-parameters from FEM simulation (or from real measurements) and need to attach that data to the design it describes — without bloating the GDS, and without depending on features that don't survive a fabrication round trip. kcq.utils.metadata provides the pointer mechanism today; the analysis that would populate it (Phase 6) is still planned.

attach_pointer(cell, layout, component_type, params) (called automatically by Transmon) writes a short "kcq:<id>" text label on the MetaRef layer (110/3) — a stable hash of the component type and parameters, so identical instances share one ID. This was deliberately built as a text label, not a KLayout cell property: verified directly (not assumed) that cell/shape properties survive an OASIS round trip but are lost on a plain GDS2 write/read, while text labels survive both. Read it back with read_pointer(cell, layout).

The actual simulation data is never embedded in the GDS: write_metadata(metadata_id, data, metadata_dir) and read_metadata(metadata_id, metadata_dir) read/write a sidecar JSON file per ID (participation ratios, extracted EJ/EC/f₀₁/anharmonicity, a reference to a Touchstone file for S-parameters, source, timestamp) in a directory you choose — keeping the GDS small and the metadata human-readable and diffable as text.

10. Netlist extraction and export (LVS) planned — Phase 4

Not implemented yet. Described here so the manual stays a complete reference to where kcq is headed.

The intended workflow: kcq.lvs.extractor.extract_connectivity(top_cell, layout) will walk the cell hierarchy, collect every instance's pins (via kcq.geometry.pins.get_pins, already available today), and union pins that coincide into nets — producing a NetlistGraph whose edges are tagged galvanic (connected by a routed CPW) or capacitive (close but unconnected, e.g. a coupled qubit pad). kcq.lvs.export.to_spice and to_touchstone will render that graph to standard formats (the latter only meaningfully once Phase 6 attaches real S-parameter results), and kcq.lvs.compare.compare(layout_graph, intended_schematic) will diff the extracted netlist against an intended one, reporting missing/extra nets and component mismatches — standard LVS-style verification, adapted for lumped-element cQED circuits.

11. Verification and design for test (DFT) planned — Phase 5

Not implemented yet.

Planned automated checks: CPW impedance consistency (computed via conformal mapping from waveguides.xml dimensions and a substrate permittivity, flagging segments that drift from the target impedance); ground-plane galvanic continuity (flagging CPW/resonator crossings with no airbridge bridging the resulting ground islands); launcher pitch against standard PCB grids (1 mm, 2.54 mm, or whatever a technology declares); and automated placement/ verification of e-beam alignment marks. One piece of this — an AST-based lint enforcing kcq's own "read/write via cell.shapes(layer), never a cell.<method> shortcut" coding convention — is already built (kcq.verification.lint), just scoped to kcq's own source rather than user designs.

12. Multi-physics simulation (Elmer FEM) planned — Phase 6

Not implemented yet. Gmsh and Elmer FEM will be required as external tools — they aren't installable via pip or the Salt package manager and kcq can't vendor them; you'll need both on your PATH.

Planned pipeline: a new materials.xml (substrate permittivity, metal London penetration depth) alongside waveguides.xml; kcq.simulation.mesher extruding each 2D layer into a 3D solid and writing a Gmsh .geo script (rejecting unmerged input — the "merge geometry before writing" coding standard already enforced elsewhere exists specifically so this step doesn't produce meshing artifacts); kcq.simulation.elmer.SifWriter generating an Elmer .sif solver file (electrostatic capacitance-matrix extraction, or eigenmode full-wave); and kcq.simulation.epr implementing the Nigg et al. (2008) Energy Participation Ratio method to turn field-solution output into estimated qubit frequency, anharmonicity, and cross-Kerr couplings — ready to attach via kcq.utils.metadata.write_metadata (available today).

13. Troubleshooting

SymptomLikely cause / fix
layout.create_cell(...) returns None Either pcell_loader.register_library("kcq") wasn't called this session, or the wrong create_cell arity was used: PCells need (name, "kcq", params); fixed (static) cells need the two-argument (name, "kcq") — the three-argument form returns None for a static cell. Also confirm the library name matches exactly ("kcq", not the technology's display name).
KcqConfigError: ... malformed XML ... Check any XML comments you've added for a literal -- — illegal per the XML spec, and easy to introduce by accident when writing prose notes inline.
InvalidGeometryError: ... bend radius ... does not fit ... The waypoints between two ports are too close together for the requested bend radius. Space the components farther apart, reduce bend_radius, or pass an aligned coupler_y_offset/position so the route is straight and needs no bend at all.
InvalidGeometryError: ... hairpin turn ... The two ports' geometry forces a literal 180° reversal at some corner (e.g. two colinear ports both needing to backtrack) — not expressible as an inscribed bend. Reposition one of the ports, or route in two shorter hops via an intermediate point.
pins.check_alignment(...) returns False unexpectedly Remember port angles are in the outward convention: a correctly-mating pair differs by 180°, not 0°. If one pin came from a placed instance, make sure you added the instance's own rotation to the pin's local angle (see the getting-started example).
